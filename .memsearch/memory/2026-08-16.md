- User asked why the dashboard still shows a finished run as live despite the backend correctly reporting it as complete.
- Claude Code identified the root cause in `components/Dashboard.tsx` at line 134: a latch mechanism that holds the "live" state, where the `observedLive` check (rule 2) fires before the `terminal` check (rule 3) in the rule order.
- Found that `wantLiveFromUrl` (the `?live=1` URL parameter) is set permanently when a run starts and never expires, causing `observedLive` to always be true even after the run finishes.
- Discovered the self-sealing behavior: `changeView` rewrites `live=1` back into the URL via `buildDashUrl`, perpetuating the problem on tab switches and reloads.
- Noted that the existing test suite locks in this buggy behavior with a test asserting that `observedLive` wins over terminal flags.
- Proposed a fix to add `&& (wantLiveFromUrl && !terminal)` condition so the URL-driven live flag clears upon actual completion, while preserving latch protections against blips.
- Separately found that the 497 vs 282 second slowdown was caused by OSRM's 6.4 GB routing graph sitting 60% in swap, triggering 56,839 major page faults across 40 route queries (~1,400 disk reads per query).
- Measured OSRM route latency improved from ~100 ms to 0.3 ms (250× improvement) after restarting the container, with a verification probe running to confirm end-to-end scenario performance.
